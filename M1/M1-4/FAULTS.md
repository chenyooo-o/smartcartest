# M1-4 故障记录手册

## 记录说明

本文件记录 M1-4 图像处理链路调优过程中实际发现并验证的问题。

每条故障按照以下五项格式记录：

1. 现象：记录故障表现、测试命令和实际测试结果。
2. 定位过程：记录排查步骤、检查内容和排除过程。
3. 根因：说明导致问题的具体原因及技术原理。
4. 修复：说明修改的文件、代码和解决方法。
5. 验证：记录修复前后的测试结果，确认问题是否解决。

注意：性能优化记录必须以实际测试数据为依据，不得编造故障或测试结果。

## 故障 1：相机图像生成速度过慢，输入频率未达到 30Hz

### ① 现象

项目原始版本运行时，相机节点的图像生成速度较慢，实际输入频率没有达到任务要求的 30Hz。

原始性能汇总记录：

文件：baseline.txt

原始相机平均频率约为：

11.9 Hz

相机目标频率：

30 Hz

测试时通过观察 camera_pub.py 输出的 `[CAMERA]` 统计信息判断相机自身发布频率。

注意：baseline.txt 保存的是原始性能汇总数据，不是完整逐行终端日志。

### ② 定位过程

检查原始相机程序备份：

backup/camera_pub_original.py

发现原始 capture() 函数使用两层 Python for 循环逐像素生成图像。

图像分辨率为：

640 × 480 = 307200 个像素

每一帧都需要通过 Python 循环逐个处理大量像素，循环执行开销较大。

排查后确认，图像生成函数是相机输入频率较低的重要性能瓶颈。

### ③ 根因

原始程序使用 Python 双层循环生成图像。

Python 逐像素循环存在较大的解释器执行开销，无法高效利用 NumPy 底层数组运算能力。

当每秒需要生成 30 张 640×480 图像时，逐像素循环造成的计算开销明显影响相机定时发布。

### ④ 修复

修改文件：

camera_pub.py

修改 capture() 函数，使用 NumPy 数组广播和向量化运算代替逐像素 Python 循环。

主要修改：

- 使用 np.arange() 生成横纵坐标数组。
- 利用 NumPy 广播机制一次性计算整张图像的像素值。
- 使用 uint8 数组存储图像。
- 保留原来的 640×480 图像分辨率。
- 不降低相机定时器的目标频率。

### ⑤ 验证

修复前：

相机输入频率约为 11.9 Hz。

修复后：

相机独立运行时，观察到的稳定平均频率约为 29.99 Hz。

性能提升约为原来的 2.52 倍。

验证结论：

相机图像生成速度得到明显改善，稳定运行时达到接近 30 Hz 的目标。

## 故障 2：图像处理速度过慢，输出频率未达到 30Hz

### ① 现象

原始版本中，图像处理节点输出频率较低，无法达到任务要求的 30 Hz。

原始性能汇总记录：

文件：baseline.txt

测试命令：

ros2 topic hz /perception/result

原始测试结果：

平均频率约为 2.21 Hz

最小消息间隔约为 0.412 s

最大消息间隔约为 0.575 s

注意：上述数据来自 baseline.txt 中保存的原始性能汇总，不是完整逐行终端日志。

### ② 定位过程

检查原始图像处理程序备份：

backup/image_proc_original.py

发现原始程序存在以下处理步骤：

1. 将输入的 640×480 灰度图放大到 1280×720。
2. 使用双层 Python for 循环逐像素增加亮度。
3. 再使用双层 Python for 循环逐像素进行对比度增强。
4. 将处理结果重新缩小到 640×480。
5. 转换为 ROS Image 消息并发布。

放大后的图像包含更多像素，逐像素循环需要处理大量数据。

同时，图像放大和缩小增加了额外计算开销。

检查优化后的代码，确认已经改用 NumPy 向量化运算。

### ③ 根因

原始程序在图像处理过程中使用 Python 双层循环逐像素执行亮度和对比度计算。

此外，原始程序先将图像放大到 1280×720，再缩小回 640×480，产生了不必要的图像处理开销。

这些操作共同导致图像处理速度下降，输出频率远低于 30 Hz。

### ④ 修复

修改文件：

image_proc.py

主要修改：

1. 删除不必要的图像放大和缩小操作，直接处理原始 640×480 图像。
2. 使用 NumPy 向量化运算代替逐像素 Python 循环。
3. 使用 np.clip() 限制像素值范围为 0～255。
4. 使用 astype(np.uint8) 转换图像数据类型。
5. 使用 cv_bridge 将结果转换为 mono8 编码的 ROS Image 消息。
6. 保留输入图像的 header.stamp 和 header.frame_id。

亮度增强：

brightened = np.clip(
    gray.astype(np.int16) + 20,
    0,
    255
)

对比度增强：

contrasted = np.clip(
    ((brightened - 128) * 3) // 2 + 128,
    0,
    255
).astype(np.uint8)

### ⑤ 验证

修复前：

图像输出平均频率约为 2.21 Hz。

最小消息间隔约为 0.412 s。

最大消息间隔约为 0.575 s。

修复后：

图像输出平均频率约为 30 Hz。

在优化测试记录中，平均频率稳定在 30 Hz 左右。

最小消息间隔约为 0.004 s。

最大消息间隔约为 0.066 s。

图像分辨率保持 640×480，编码为 mono8。

验证结论：

图像处理性能明显提升，输出频率达到任务要求的 30 Hz。

## 故障 3：图像链路消息队列积压，端到端延迟过高

### ① 现象

原始图像处理链路运行时，图像输出延迟较高。

原始测试命令：

ros2 topic delay /perception/result

原始性能汇总记录：

文件：baseline.txt

原始平均延迟约为 3.07 s。

原始最小延迟约为 2.696 s。

原始最大延迟约为 3.562 s。

在后续优化实验中，进一步观察到图像订阅端 QoS 队列深度较大，可能导致处理速度跟不上消息到达速度时产生旧消息积压。

### ② 定位过程

检查文件：

image_proc.py

发现图像订阅端原先使用：

make_sub_qos()

该函数默认队列深度为：

depth=30

当图像以约 30 Hz 的速度持续到达，而处理节点无法及时处理全部历史消息时，队列中可能积累较旧的图像。

对于实时图像处理任务，处理过时图像会增加端到端延迟。

随后进行 QoS 队列深度调整实验，并通过以下命令检查延迟：

ros2 topic delay /perception/result

### ③ 根因

图像订阅端使用较大的历史消息队列。

在处理速度与消息到达速度不匹配时，旧图像可能在队列中等待处理。

实时控制和视觉处理通常更关注最新图像，而不是完整处理所有历史图像。

因此，较大的队列深度可能导致消息积压，增加端到端延迟。

### ④ 修复

修改文件：

image_proc.py

将图像订阅端 QoS 队列深度从 30 调整为 1。

修改后的订阅代码：

self.sub = self.create_subscription(
    Image,
    IMAGE_IN,
    self.on_image,
    make_sub_qos(depth=1)
)

保留图像输出发布端和控制发布端原有 QoS 配置。

这样可以减少图像订阅端积压的历史消息，使处理节点优先处理较新的图像。

### ⑤ 验证

调整队列深度前：

后续 depth=30 对照实验中：

最大延迟约为 1.028 s。

调整队列深度后：

测试命令：

ros2 topic delay /perception/result

测试记录文件：

measurements/depth1_image_delay.txt

测试结果：

平均延迟约为 0.014～0.016 s。

最小延迟约为 0.003 s。

最大延迟约为 0.039 s。

最大延迟从约 1.028 s 降低到约 0.039 s。

验证结论：

将图像订阅队列深度调整为 1 后，消息积压明显减少，端到端延迟大幅降低，满足低延迟图像处理的优化方向。

注意：上述 ros2 topic delay 输出提供的是平均值、最小值、最大值和标准差，不是 P95。P95 需要通过单独采样程序计算，不能将最大延迟当作 P95。

## 故障 4：节点非预期消失，导致 ROS 2 话题不存在

### ① 现象

检查 M1-4 图像处理链路时，发现 ROS 2 节点列表为空，控制话题和相机输入话题均不存在。

执行命令：
- ros2 node list
- ros2 topic info /control/cmd
- ros2 topic info /camera/image_raw

当时终端输出：

```text
========== 节点列表 ==========

========== 控制话题信息 ==========
Unknown topic /control/cmd

========== 图像话题信息 ==========
Unknown topic /camera/image_raw
```

### ② 定位过程

首先执行 ros2 node list，检查当前 ROS 2 节点，结果为空。

随后检查 /control/cmd 和 /camera/image_raw，均返回 Unknown topic，确认检查时相关节点和话题没有建立。

### ③ 根因

本次检查时，相机节点和图像处理节点没有运行，导致相机输入、图像输出和控制链路无法正常工作。

目前能够确认的是检查时节点未启动；此前节点未运行的具体原因没有进一步证据，因此不推断为程序崩溃或执行器阻塞。

### ④ 修复

重新启动相机节点：
python3 camera_pub.py

再启动图像处理与控制节点：
python3 image_proc.py

保持两个终端持续运行。

### ⑤ 验证

重新执行 ros2 node list，实际输出：

/camera_sim
/control_loop
/image_proc

检查 /control/cmd：

Type: geometry_msgs/msg/Twist
Publisher count: 1
Subscription count: 0

检查 /camera/image_raw：

Type: sensor_msgs/msg/Image
Publisher count: 1
Subscription count: 1

检查 /perception/result：

Type: sensor_msgs/msg/Image
Publisher count: 1
Subscription count: 0

验证结论：

重新启动节点后，三个节点均出现在 ROS 2 节点列表中，图像输入、图像输出和控制话题均已建立，链路恢复。

## 故障：相机话题接收频率异常偏低（根因待定位）

### ① 现象

此前相机节点自身统计的发布频率约为 29～30 Hz，但使用 `ros2 topic hz /camera/image_raw` 测量时，接收频率只有约 5.3～6.2 Hz。image_proc 的输入和输出频率也曾下降至约 2～15 Hz。

P95 测量曾在 60 秒内只采集到 366 帧，未达到 600 帧目标。

### ② 定位过程

1. 使用 `ps -ef` 检查进程，确认 camera_pub.py 和 image_proc.py 各运行一个，未发现重复进程。
2. 使用 `top` 检查系统资源，CPU 空闲率为 94.9%，可用内存约 9026.6 MiB，Swap 使用量为 0，未发现明显资源不足。
3. 相机节点自身日志显示发布频率约为 29～30 Hz。
4. `ros2 topic hz /camera/image_raw` 测得接收频率约为 5.3～6.2 Hz。
5. 检查话题 QoS，camera_sim 发布端与 image_proc 订阅端均为 RELIABLE，未发现可靠性策略不兼容。
6. 发现额外订阅者 `_ros2cli_4871`，确认其为 `ros2 topic hz` 测量进程。停止该进程后，话题只剩 image_proc 一个订阅者，但当时尚未完成验证。
7. 关闭终端并重新启动测试后，相机单独运行时连续多个窗口保持约 30 Hz。
8. 同时运行相机和 image_proc 后，图像处理输入、输出频率恢复至约 27～30 Hz，输入输出帧数一致。
9. P95 测量期间，image_proc 频率保持约 29.01～30.34 Hz。
10. 本轮 P95 成功采集 600 帧：平均延迟 18.257 ms，P95 延迟 23.446 ms，最大延迟 61.204 ms，最小延迟 3.473 ms，负延迟样本数为 0。

### ③ 根因

尚未确定。

目前只能确认重新启动节点后图像链路恢复稳定。没有充分证据证明额外订阅者、QoS、CPU 资源或某个具体代码位置是最初低频现象的根因。

### ④ 修复

通过关闭原有终端并重新启动相机和图像处理节点，图像链路恢复稳定。

本次没有修改相机发布频率、图像处理代码或 QoS 配置。该操作属于恢复措施，不能视为已经查明并彻底修复根因。

### ⑤ 验证

1. 相机单独运行时，连续统计窗口约为 29.97～30.05 Hz。
2. 相机与 image_proc 同时运行时，输入和输出频率约为 27.01～30.00 Hz，输入输出帧数一致。
3. P95 测量期间，image_proc 输入和输出频率约为 29.01～30.34 Hz，输入输出帧数一致。
4. P95 测量成功采集 600 帧，P95 为 23.446 ms，小于 200 ms 的验收上限。
5. 本轮测量数据保存于：
   - `measurements/p95_test_output_20261122.log`
   - `measurements/p95_samples_20261122.csv`

验证结论：当前重新启动后的图像链路和 P95 指标达到本轮测试要求；最初低频现象的根因仍待后续复现和定位。
